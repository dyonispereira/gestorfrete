# 039 — CT-e (Conhecimento de Transporte Eletrônico)

Bounded context proprietário: `documents` (D215). Máquina de estados canônica em
[`../flows/009-FISCAL.md`](../flows/009-FISCAL.md) seção "Máquina de Estados — CT-e", DDL em
[`../database/relational/007-fiscal.md`](../database/relational/007-fiscal.md), RBAC em
`RBAC_MATRIX.md` §7.17 — todos lidos por completo antes de escrever este documento (D200 aplicado à
API).

## D280 — Viagem mantém só a projeção fiscal resumida

Por D106, o CT-e tem máquina de estados própria (8 estados) — mais granular que o `Status Fiscal`
resumido que a Viagem expõe (`PENDENTE`/`AUTORIZADO`/`CANCELADO`/`DENEGADO`, já `readOnly` em
`018-trip-status.md`, projeção D081). Este documento é a fonte de verdade granular; a Viagem nunca
duplica o detalhe, só reflete o resumo.

## Sem `POST /ctes`

A criação do CT-e (`status = RASCUNHO`) é disparada automaticamente pelo consumidor de
`ViagemDespachada` (`freight`) — não existe um comando manual de "criar CT-e do zero" no domínio
(`009-FISCAL.md`, "Gatilho inicial"). Todos os comandos abaixo operam sobre um CT-e que já existe.

## `GET /api/v1/ctes`

**Segurança**: `bearerAuth` + `documents.cte.view`.

**Query parameters**: `page`/`limit`, `trip_id` (`viagem_id`), `status`, `series` (`serie`),
`access_key` (`chave_acesso`).

**Responses**: `200` (`Pagination` de `CTe`, `fiscal-schemas.md`), `401`, `403`, `500`.

## `GET /api/v1/ctes/{id}`

**Responses**: `200` (`CTe`), `401`, `403`, `404`, `500`.

## Máquina de estados — comandos

**D274 — nenhum comando altera `status` via corpo; cada transição é um verbo próprio.** RBAC
`documents.cte` é coarse-grained (`.view`/`.issue`/`.cancel`/`.correct`/`.export` — sem código por
sub-passo de emissão) — `validate`/`sign`/`transmit`/`inutilize` reaproveitam `.issue` (mesmo
raciocínio de `026-maintenance-orders.md`, D240-precedente: "Emissão" cobre toda a sequência
RASCUNHO→TRANSMITIDO, `009-FISCAL.md` seção Permissões trata como uma única responsabilidade do
Faturista).

| De | Para | Comando | RBAC |
|---|---|---|---|
| `RASCUNHO` | `VALIDADO` | `commands/validate` | `.issue` (sem código dedicado) |
| `VALIDADO` | `ASSINADO` | `commands/sign` | `.issue` (sem código dedicado) |
| `ASSINADO` | `TRANSMITIDO` | `commands/transmit` | `.issue` (sem código dedicado) |
| `TRANSMITIDO` | `AUTORIZADO`/`DENEGADO` | `commands/receive-sefaz-response` | `.receive_sefaz_response` |
| `AUTORIZADO` | `CANCELADO` | `commands/cancel` | `.cancel` |
| `RASCUNHO`/`VALIDADO` | `INUTILIZADO` | `commands/inutilize` | `.issue` (sem código dedicado) |

### `commands/validate`

`RASCUNHO → VALIDADO`. Confere dados obrigatórios contra o schema XML da SEFAZ — validação
estrutural, não envio.

**Responses**: `200` (`CTe`, D238), `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION` /
`FISCAL_CTE_VALIDATION_FAILED` (dados incompletos/inconsistentes), `500`.

### `commands/sign`

`VALIDADO → ASSINADO`. Aplica a assinatura digital usando o certificado de `045-configuracao-
fiscal.md` — **nunca aceita certificado no corpo da requisição** (D279, a API só referencia
`certificado_arquivo_id` já configurado, nunca recebe segredo via payload).

**Responses**: `200`, `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION` /
`FISCAL_CERTIFICATE_EXPIRED`, `500`.

### `commands/transmit`

`ASSINADO → TRANSMITIDO`. Envia à SEFAZ (via `documents` → integração, D278 — este endpoint nunca
fala com a SEFAZ diretamente). A resposta (autorização/denegação) chega de forma assíncrona, via
`044-eventos-fiscais.md` consumido internamente — a resposta deste comando reflete `TRANSMITIDO`,
não já `AUTORIZADO`/`DENEGADO` (D238 aplicado ao que já é conhecido no momento da resposta HTTP,
nunca adivinhando o resultado assíncrono).

**Segurança**: idem. **Idempotency-Key**: obrigatório (D211 — transmitir duas vezes não pode gerar
dois protocolos). **D275**: `protocolo_sefaz` é a segunda camada de idempotência, em nível de
domínio (`uq_ctes_protocolo_sefaz`) — reprocessar a mesma resposta da SEFAZ (reentrega, timeout
seguido de retry) nunca grava uma segunda transição, mesmo que o `Idempotency-Key` HTTP não tenha
sido reaproveitado pelo cliente.

**Responses**: `200`, `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION`, `500`, `502` —
`FISCAL_SEFAZ_UNAVAILABLE` (contingência, fora do escopo detalhado desta fundação).

### `commands/receive-sefaz-response` — Reconciliado (D397, Lote Fiscal Parte 2.2)

`TRANSMITIDO → AUTORIZADO`/`DENEGADO`. Resultado da SEFAZ — **continua**, na essência, um evento
assíncrono externo, nunca uma decisão do cliente (D277/D278 mantidos: nenhum payload de decisão é
aceito aqui, o resultado vem do `SefazGateway`, não do corpo da requisição). O que muda é que agora
existe uma fronteira HTTP real para receber essa resposta — antes, o método de domínio
(`FiscalInternalTransitions.receive_cte_sefaz_response`) só era acionável em teste, o que também
bloqueava geneticamente o caminho Viagem→CT-e→Fatura para qualquer usuário real (gap identificado
no Lote Financeiro, Parte 2, fechado aqui).

Nenhuma integração real com a SEFAZ existe nesta fundação (sem certificado, sem cliente SOAP/REST,
sem assinatura XML) — o `SefazGateway` (port, `modules/documents/domain/gateways`) hoje só tem
`SandboxSefazGateway` como implementação, que **sempre autoriza**, de forma determinística e
claramente identificável (`protocolo_sefaz` prefixado `SANDBOX-`). Trocar pelo provider real,
quando existir, não muda este endpoint nem toca `domain`/`application` — só o adapter.

**Sem corpo de requisição** — o resultado vem inteiramente do gateway, nunca de um payload do
cliente (isso seria o cliente decidindo a resposta da SEFAZ, o que D277/D278 sempre proibiram).

**Segurança**: `documents.cte.receive_sefaz_response` — código novo, não reaproveita `.issue`
propositalmente: representa um evento de sistema/simulação, não uma ação de emissão do Faturista.

`AUTORIZADO` publica `CTeEmitido`; `DENEGADO` publica `CTeDenegado` (ambos já em `EVENT_MAP.md`).

**Responses**: `200` (`CTe`), `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION`, `500`.

### `commands/cancel`

`AUTORIZADO → CANCELADO`. Só dentro do prazo legal de cancelamento (validação de aplicação,
`009-FISCAL.md`) — **D282**: cancelamento nunca é usado para corrigir um erro formal (isso é Carta
de Correção, `042-carta-correcao.md`) nem confundido com denegação (resposta negativa da própria
SEFAZ) ou inutilização (numeração nunca transmitida).

```yaml
requestBody:
  required: true
  content:
    application/json:
      schema:
        type: object
        properties:
          notes: { type: string }
        required: [notes]
```

**Segurança**: `documents.cte.cancel` (Aprovação: Diretor — RBAC marca criticidade Alta).
**Idempotency-Key**: obrigatório.

**Responses**: `200`, `400`, `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION` /
`FISCAL_CTE_CANCEL_DEADLINE_EXPIRED`, `500`.

### `commands/inutilize`

`RASCUNHO`/`VALIDADO → INUTILIZADO`. Número reservado que nunca será transmitido (falha de sistema,
mudança de plano) — a numeração da SEFAZ não pode ter buracos silenciosos (`009-FISCAL.md`).
**D282**: semanticamente distinto de `CANCELADO` (que reverte algo já `AUTORIZADO`).

**Responses**: `200`, `401`, `403`, `404`, `409` — `FISCAL_CTE_INVALID_TRANSITION`, `500`.

**Nota**: `flows/009-FISCAL.md` não cataloga um evento próprio para esta transição (ao contrário das
outras sete) — `EVENT_MAP.md` também não o tem. Diferente da família de gaps D194–D284 (onde o fluxo
nomeia algo que o artefato downstream não tem), aqui o próprio fluxo nunca nomeou o evento — tratado
como escopo deliberado do Domain (inutilização é correção de numeração, baixo valor de broadcast
entre bounded contexts), não como lacuna a corrigir.

## Transições inválidas (reforço)

- `CANCELADO`/`INUTILIZADO` nunca retornam a qualquer estado anterior — nenhum comando os aceita
  como origem.
- Não existe comando que pule `ASSINADO`/`TRANSMITIDO` — `VALIDADO → AUTORIZADO` direto não é
  alcançável por nenhum endpoint.
- Um CT-e `DENEGADO` nunca é reemitido como o mesmo registro — a correção gera um novo CT-e (via o
  mesmo consumidor de `ViagemDespachada`, fora do controle direto do cliente HTTP).

## `GET /api/v1/ctes/{id}/status-history`

Leitura pura (D281), cursor-paginado (Categoria Física Histórica).

**Segurança**: `documents.cte.view` (sem código dedicado de "ver histórico", mesmo padrão de
`030-maintenance-history.md`).

**Query parameters**: `cursor`, `limit`, `status`.

**Responses**: `200` (coleção cursor-paginada de `CTeStatusHistoryEntry`, `fiscal-schemas.md`),
`401`, `403`, `404`, `500`. **Sem `POST`/`PATCH`/`DELETE`** (D281).

## `GET /api/v1/ctes/{id}/xml`

**D276** — nunca o XML embutido na entidade. Este endpoint referencia o artefato, não serve o
binário diretamente (contrato de Storage ainda não tem lote próprio — ver nota).

**Segurança**: `documents.cte.view`.

```yaml
"200":
  description: Referência ao XML autorizado
  content:
    application/json:
      schema:
        type: object
        properties:
          xml_file_id: { $ref: "components/schemas.md#/UUID" }
          generated_at: { $ref: "components/schemas.md#/Timestamp" }
        required: [xml_file_id]
```

`401`, `403`, `404` — CT-e ainda não tem XML (antes de `AUTORIZADO`), `500`.

## Fora de escopo, não esquecido

- **Download binário do XML**: sem contrato de Storage próprio ainda — este lote só resolve a
  referência (`xml_file_id`), nunca serve o arquivo.
- **Emissão em modo de contingência** (SEFAZ indisponível): `009-FISCAL.md`, "Requisitos futuros".
- **`documents.sefaz_status.view`**: sobreposto conceitualmente com `documents.cte.view` (o status
  já vem em `GET /ctes/{id}`) — sem endpoint próprio, RBAC mantido para uso futuro se um endpoint de
  consulta ao vivo à SEFAZ for pedido.

## Como este documento cresce

Se `documents.document_type.view` (RBAC §7.17) ganhar uma entidade física própria no futuro (hoje é
só o Enum `eventos_fiscais_documento_tipo_enum`), um `GET /fiscal/document-types` é candidato — não
construído agora por não existir tabela correspondente (D101/D102).
