# 011 — BI

Traduz para SQL as 9 entidades de [`../dictionary/011-bi.md`](../dictionary/011-bi.md). As 8 regras
de [`../README.md`](../README.md) já se aplicam a toda tabela. Um dos lotes mais simples da sprint,
como esperado — a separação Analytics/Reporting já vinha pronta do Domain.

**Regra que atravessa o arquivo inteiro (D090, reforçada mais uma vez)**: nenhuma tabela deste lote
é referenciada por FK a partir de uma tabela operacional (`viagens`, `ordens_servico`, etc.) — a
leitura é sempre no sentido BI → operação (consultando/consumindo eventos), nunca o contrário.
Nenhuma métrica operacional (custo, margem, disponibilidade) é persistida aqui; ela já vive nas
tabelas de negócio (`viagens.margem_realizada`, por exemplo) e é apenas **lida** por `metricas`.

# Analytics

## `metricas`

```sql
CREATE TYPE metricas_granularidade_temporal_enum AS ENUM ('DIARIO', 'SEMANAL', 'MENSAL', 'POR_EVENTO');
CREATE TYPE metricas_granularidade_dimensional_enum AS ENUM ('VIAGEM', 'VEICULO', 'MOTORISTA', 'CLIENTE', 'TENANT');
CREATE TYPE metricas_periodicidade_calculo_enum AS ENUM ('TEMPO_REAL', 'INCREMENTAL', 'DIARIO', 'MANUAL');

CREATE TABLE metricas (
    id                          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id                   UUID REFERENCES tenants(id),   -- nulo quando Platform Reference Data (D046)
    nome                        TEXT NOT NULL,
    formula                     TEXT NOT NULL,
    versao                      INTEGER NOT NULL DEFAULT 1,     -- D155 — nunca decresce
    granularidade_temporal       metricas_granularidade_temporal_enum NOT NULL,
    granularidade_dimensional    metricas_granularidade_dimensional_enum NOT NULL,
    unidade                      TEXT NOT NULL,
    origem_dados                  JSONB NOT NULL,   -- D150 — quais bounded contexts/campos alimentam
    periodicidade_calculo         metricas_periodicidade_calculo_enum NOT NULL,
    status                        TEXT NOT NULL DEFAULT 'ATIVA'
);
```

## `indicadores_consolidados`

```sql
CREATE TYPE indicadores_consolidados_status_enum AS ENUM ('VALIDO', 'RECALCULADO', 'SNAPSHOTADO');

CREATE TABLE indicadores_consolidados (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id           UUID NOT NULL REFERENCES tenants(id),
    metrica_id          UUID NOT NULL REFERENCES metricas(id),
    metrica_versao      INTEGER NOT NULL,   -- D156 — cópia fixa, nunca a fórmula em si
    dimensao_tipo       TEXT NOT NULL,
    dimensao_id         UUID NOT NULL,      -- polimórfico, sem FK
    periodo_referencia  TEXT NOT NULL,
    valor               NUMERIC(18,4) NOT NULL,
    data_hora_calculo    TIMESTAMPTZ NOT NULL DEFAULT now(),
    status               indicadores_consolidados_status_enum NOT NULL DEFAULT 'VALIDO'
);

CREATE INDEX idx_indicadores_consolidados_metrica_dimensao
    ON indicadores_consolidados (metrica_id, dimensao_tipo, dimensao_id, periodo_referencia);
```

`status = 'SNAPSHOTADO'` é o gatilho de imutabilidade — a partir daí, nenhum processo recalcula ou
sobrescreve esta linha (reforçado na aplicação, D151); um novo período/recálculo sempre insere uma
nova linha, nunca faz `UPDATE` no `valor` de uma linha `SNAPSHOTADO`.

## `snapshots_analiticos` e `snapshots_analiticos_indicadores`

```sql
CREATE TYPE snapshots_analiticos_origem_processamento_enum AS ENUM ('AUTOMATICO', 'MANUAL');
CREATE TYPE snapshots_analiticos_status_enum AS ENUM ('EM_PROCESSAMENTO', 'CONSOLIDADO', 'INVALIDO');

CREATE TABLE snapshots_analiticos (
    id                          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id                   UUID NOT NULL REFERENCES tenants(id),
    periodo_referencia           TEXT NOT NULL,
    data_hora_consolidacao        TIMESTAMPTZ,
    origem_processamento          snapshots_analiticos_origem_processamento_enum NOT NULL,
    usuario_id                    UUID REFERENCES usuarios(id),   -- obrigatório (aplicação) quando MANUAL
    status                        snapshots_analiticos_status_enum NOT NULL DEFAULT 'EM_PROCESSAMENTO'
);

-- D160 — quais Métricas (e versões) participaram, via junção com indicadores já versionados
CREATE TABLE snapshots_analiticos_indicadores (
    snapshot_analitico_id       UUID NOT NULL REFERENCES snapshots_analiticos(id),
    indicador_consolidado_id     UUID NOT NULL REFERENCES indicadores_consolidados(id),

    PRIMARY KEY (snapshot_analitico_id, indicador_consolidado_id)
);
```

Um trigger `AFTER INSERT ON snapshots_analiticos_indicadores` (ou lógica de aplicação) marca o
`indicador_consolidado.status = 'SNAPSHOTADO'` no momento em que ele entra em um snapshot
`CONSOLIDADO` — detalhe de implementação em `MIGRATIONS.md`.

## `cubos_analiticos` e `cubos_analiticos_metricas`

```sql
CREATE TABLE cubos_analiticos (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       UUID NOT NULL REFERENCES tenants(id),
    nome            TEXT NOT NULL,
    dimensoes       JSONB NOT NULL,   -- ex: ["Tempo", "Veículo", "Motorista", "Cliente", "Filial"]
    status          TEXT NOT NULL DEFAULT 'ATIVO',

    CONSTRAINT uq_cubos_analiticos_tenant_id_nome UNIQUE (tenant_id, nome)
);

CREATE TABLE cubos_analiticos_metricas (
    cubo_analitico_id   UUID NOT NULL REFERENCES cubos_analiticos(id),
    metrica_id           UUID NOT NULL REFERENCES metricas(id),

    PRIMARY KEY (cubo_analitico_id, metrica_id)
);
```

Apenas a definição estrutural (dimensões/medidas) — nenhuma tabela de dados materializados do cubo
nesta fundação (a própria entidade de domínio já é só metadado, ver `dictionary/011-bi.md`).

## `exportacoes_geradas`

Contexto completo (D157) — filtros, período, usuário, versão das métricas, sempre presentes.

```sql
CREATE TYPE exportacoes_geradas_status_enum AS ENUM ('PROCESSANDO', 'CONCLUIDA', 'FALHOU');

CREATE TABLE exportacoes_geradas (
    id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id               UUID NOT NULL REFERENCES tenants(id),
    relatorio_salvo_id       UUID REFERENCES relatorios_salvos(id),
    usuario_id                UUID NOT NULL REFERENCES usuarios(id),
    filtros_utilizados         JSONB NOT NULL,
    periodo                    TEXT NOT NULL,
    metricas_versoes           JSONB NOT NULL,   -- [{metrica_id, versao}, ...] — D157/D160
    arquivo_id                 UUID,             -- D107, obrigatório (aplicação) em CONCLUIDA
    mensagem_erro              TEXT,             -- observabilidade — preenchido quando status = FALHOU
    data_hora_solicitacao       TIMESTAMPTZ NOT NULL DEFAULT now(),
    status                      exportacoes_geradas_status_enum NOT NULL DEFAULT 'PROCESSANDO'
);

CREATE INDEX idx_exportacoes_geradas_usuario_id ON exportacoes_geradas (usuario_id, data_hora_solicitacao DESC);
```

`mensagem_erro` é a primeira aplicação do padrão de observabilidade sugerido para as tabelas
técnicas do projeto (`logs_auditoria`, `eventos_fiscais`, `execucoes_job`, ...) — sem forçar um
documento próprio agora, só adotando o campo onde já faz sentido natural (um `status = FALHOU`
sem motivo registrado é exatamente o tipo de lacuna que essas tabelas técnicas devem evitar).

## `agendamentos_atualizacao`

```sql
CREATE TYPE agendamentos_atualizacao_modo_enum AS ENUM ('TEMPO_REAL', 'INCREMENTAL', 'DIARIO', 'MANUAL');

CREATE TABLE agendamentos_atualizacao (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id           UUID NOT NULL REFERENCES tenants(id),
    metrica_id          UUID REFERENCES metricas(id),
    cubo_analitico_id   UUID REFERENCES cubos_analiticos(id),
    modo                agendamentos_atualizacao_modo_enum NOT NULL,
    status              TEXT NOT NULL DEFAULT 'ATIVO',

    CONSTRAINT ck_agendamentos_atualizacao_alvo
        CHECK ((metrica_id IS NOT NULL)::int + (cubo_analitico_id IS NOT NULL)::int = 1)
    -- nunca executa cálculo (D159) — só referencia o alvo e a política; quem calcula é analytics,
    -- disparado via execucoes_job (010-administracao.md)
);
```

## Constraints de integridade — resumo

| Regra de negócio | Constraint física |
|---|---|
| Indicador Consolidado imutável após Snapshotado (D151) | Reforçado na aplicação — nenhum `UPDATE` de `valor` permitido quando `status = 'SNAPSHOTADO'` |
| Dashboard nunca guarda dado, só configuração (D152) | Nenhuma coluna numérica de indicador em `dashboards_personalizados` |
| Agendamento aponta para exatamente um alvo | `ck_agendamentos_atualizacao_alvo` |
| Métrica sempre versionada (D155) | `metricas.versao`, nunca sobrescrita — nova versão é uma nova linha lógica (aplicação controla, sem `UPDATE` de `formula`) |
